# 桌面启动阻塞最小修复设计

用户批准：保留 DSH 和认证方式，只修阻塞点、补回归测试、构建新版；不重启现有后端。

## 现场与范围

后端 PID 33339 已监听 3080，带日志中的认证链接请求返回 HTTP 200；桌面加载页仍停在约 48 秒。启动轮询放在 `tauri::async_runtime::spawn(async move { ... })` 中，但整个循环没有 await，使用 reqwest::blocking 和 std::thread::sleep。本地 reqwest 文档明确禁止在 async runtime 任务内执行 blocking API。

## 方案

将完整同步启动轮询交给 blocking worker，保持已有请求超时、认证 cookie、进程归属、失败清理与页面导航语义。用可测试的启动调度入口约束此线程边界。先通过重复本机 HTTP 探测复现并定位，再采用最小修改。不全面改写为 async，不重新下载包，不修改用户配置。

## 验证与交付

回归测试覆盖 worker 内多于 128 次请求仍能完成，HTTP 不响应仍能超时；源码约束确保启动循环走该入口。保留现有 Python 和 Rust 测试。构建 app，交付路径；未经确认不退出当前正在使用的应用或后端。

## 复现结果与重启验收补充

- Release 最小复现：同一 async task 内重复构造并销毁 reqwest blocking client，第 128 次后停住，外部 5 秒看门狗报超时；换用生产 spawn_boot_worker 后 160 次全部完成。
- Debug 回归：旧调度在 async context 内阻塞触发 Tokio panic；修复后 160 次真实本机 HTTP 探测与无响应超时测试均通过。
- 累计日志样例暴露了从头取 token 会使用旧进程 token 的兼容性问题。补两项先失败的测试，再将解析改为反向扫描、止于最新启动分隔线。认证机制本身不变。
- 用户随后同意替换已安装应用并重启验证，允许短暂中断现有后端。
